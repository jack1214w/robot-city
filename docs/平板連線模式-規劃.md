# 平板連線模式 · 規劃

> 這份文件是給「之後要動工的那個對話」看的交接文件。
> 開新對話時說一句「讀 `docs/平板連線模式-規劃.md`，在 `live-mode` 分支上做第一次交付」就能接上，不用重講背景。
>
> 撰寫日期：2026-11-17（同日更新：教室投影只能鏡像，原 Phase 0 與 Phase 1 合併為一次交付）

---

## 1. 要解決什麼

目前的遊戲是**熱椅模式**：一台筆電，學生輪流走到筆電前出牌，整個畫面（含所有人的手牌）投影給全班看。

要做的是**平板連線模式**：

- 投影畫面只顯示**地圖、計分板、執行紀錄、回合引導**
- 每個學生用**自己的平板**看自己的手牌、排程式
- 學生**看不到彼此的手牌**

### 熱椅模式必須完整保留

這不是「新版取代舊版」，兩種模式要並存，理由：

- 網路出事（投影機壞、AP 當掉、平板沒電）時當場能切回去繼續上課
- 只有一台電腦的場合：借教室、臨時加場、校外分享
- 單人練習模式本來就只需要一台機器
- **第一堂教規則時，全班盯著同一個人排程式反而好帶**——老師可以當場問「他這樣排會走到哪？」，這種集體推理在平板模式會消失

開場畫面會變成三選一：`單人練習` ／ `多人對戰（單機熱椅）` ／ `多人對戰（平板連線）`，**預設是現在的行為**。

## 2. 已經確認過的事實（不必重測）

| 項目 | 結果 | 怎麼確認的 |
|---|---|---|
| 學校網路有沒有用戶端隔離 | **沒有，可以走區網** | 2026-11-17 在教室用**學生平板**連筆電的測試伺服器，成功 |
| 學生平板 Safari 肯不肯開 `http://` 區網位址 | **可以** | 同上，平板 `192.168.50.182` → 筆電 `192.168.50.231:8080` |
| 平板上的 VPN 會不會擋區網 | **不會** | 測試當下平板狀態列有 VPN 標誌，仍然連得到 |
| 筆電有沒有 Node | **有，v25.9.0**（npm 11.12.1，`/opt/homebrew/bin/node`） | `node --version` |
| 筆電防火牆 | 目前關閉 | `socketfilterfw --getglobalstate` |
| GitHub Pages 來源 | `main` 分支、根目錄 | `gh api repos/jack1214w/robot-city/pages` |

**結論：走區網方案，不需要任何雲端服務、不需要申請任何帳號。** 學生資料完全不出教室。

### 已確認：投影只能鏡像

教室投影機**只能鏡像**，不能設延伸桌面。

影響：原本的 Phase 0（雙視窗、靠延伸桌面擋手牌）在這間教室**課堂價值歸零**，因此與 Phase 1 合併為一次交付（見第 4 節）。

**對最終成果沒有影響。** 平板連線模式下，筆電螢幕上只有投影檢視（地圖、計分、紀錄、QR code），手牌全在平板上，筆電畫面沒有任何秘密，鏡像照出去剛好就是要的東西。

### 還沒確認的

- [ ] 平板數量：每人一台還是兩人共用（共用的話保密只到「兩人一組」的程度）
- [ ] 不同教室／不同 SSID 會不會有不同結果（這次只測了一間教室）

## 3. 架構決策：主機權威 ＋ 瘦客戶端

### 為什麼這樣選

目前所有狀態集中在一個 `G` 物件，畫面由 `renderTop` / `renderProgram` / `renderHand` / `renderRail` / `paintRobots` 五個獨立函式各畫各的。**地圖動畫、規則、執行引擎（`runNodes`）一行都不用改。**

- **老師筆電 = 主機**：`G` 只有它有，所有規則判定、動畫、計分都在它身上跑（跟現在完全一樣）
- **平板 = 瘦客戶端**：只做兩件事——顯示主機發給它的東西、把學生的動作送回去

### 這樣做的三個好處

1. **手牌保密是真的保密。** 主機發給 3 號機的封包裡本來就沒有別人的手牌，學生開 devtools 也挖不到。如果反過來做成「大家共用一份狀態」，好奇的學生 30 秒就能看光全班的牌
2. **平板不用畫地圖**（地圖在投影上，最多放個縮圖）。平板只要手牌、程式區、任務卡、幾顆大按鈕——所以不是把現在的三欄版硬塞進平板做 RWD，而是另做一個精簡版面，**反而比較簡單**
3. **按下「執行」後平板鎖住，強迫全班抬頭看投影**。這對上課是好事

### 傳輸層抽象（關鍵）

**兩種模式走同一條程式路徑**，差別只在傳輸層的實作：

| 模式 | 傳輸層是什麼 |
|---|---|
| 熱椅（單機、離線可用） | 一個**直接函式呼叫**，同步、零延遲、不碰網路 |
| 平板連線 | WebSocket |

兩者的介面一樣（`send` / `onmessage`）。

> **不要做 `BroadcastChannel` 傳輸層。** 它原本只為了 Phase 0 的雙視窗存在，而教室投影只能鏡像、那個情境不成立，做了就是永遠不會上線的死程式碼。
> 驗證兩個檢視拆得對不對，改成在筆電上開兩個瀏覽器視窗、都連 `localhost` 的 WebSocket——測到的東西更多（順便驗了網路層），也少寫一套傳輸。

好處：

- 不會有兩份規則程式碼各自長歪（最怕投影畫面和平板算出不同結果）
- **熱椅模式等於一直在幫連線模式測試底層**——熱椅沒壞，代表管線是對的
- 以後改規則只要改一次

## 4. 兩次交付

> 原本規劃成 Phase 0／1／2 三個階段。因為教室投影只能鏡像，Phase 0 的課堂價值歸零，
> 它的工程價值（地基＋檢查點）又不需要使用者點頭，所以**與 Phase 1 合併成一次交付**。
> 工作內容與順序完全沒有減少，只是中間不停下來等確認。

### 第一次交付 · 平板連線可用

**做完這個就能帶進教室。** 內部順序：

1. **B 類意圖重構**（見第 5 節）＋ 把畫面拆成兩個檢視
   - **投影檢視**：地圖、計分板、執行紀錄、回合引導、QR code
   - **控制檢視**：手牌、程式區、按鈕（之後跑在平板上）
2. **內部檢查點**：熱椅模式完整回歸測試。熱椅沒壞，代表意圖管線是對的；
   這一步出問題就當場修完再往下，不要帶著走進網路層
3. 筆電跑一支小 WebSocket 伺服器，包成雙擊就能執行的 `.command`
4. 開房流程：老師按「開房」→ **投影畫面顯示大大的 QR code** →
   學生平板掃碼進房、挑座位（1 號機～7 號機）。不做帳號、不做登入
5. **C 類 pickers 改成跨網路**（見第 5 節，這是最棘手的部分）
6. 用真平板實測：連線、出牌、執行、斷線

**QR code 不是優化，要直接列進設計**：筆電 IP 每堂課可能不一樣（DHCP），
總不能每次在黑板寫一串 `192.168.x.x` 叫七個學生手打。
QR 產生器是純前端幾十行，順便把房號編進網址，連輸入房號都免了。

### 第二次交付 · 平板版面 ＋ 斷線重連

- 平板直式版面、大按鈕
- **斷線重連在教室是必須，不是加分項**：平板鎖屏、學生誤按上一頁、電量不足，
  這些一定會發生。靠 `localStorage` 記住座位，重開網頁自動回去
- 老師端主控：暫停、跳過某人、代打、把某人踢出重連

### 學生實際上怎麼操作

| | 學生在哪出牌 | 誰看得到手牌 | 投影畫面顯示 |
|---|---|---|---|
| **現在（熱椅）** | 教師筆電 | **全班**（手牌跟著投影出去） | 整個遊戲畫面，含所有人手牌 |
| **第一次交付後** | **自己的平板** | 只有自己 | 只有地圖／計分／執行紀錄／QR code |
| **第二次交付後** | 自己的平板（版面好用、斷線能回來） | 只有自己 | 同上 |

## 5. 真正的技術風險在哪

風險**不在部署**（見第 6 節），在重構。

目前學生點一張手牌是**直接改 `G`**：

```js
b.onclick = () => { G.program.push({id}); renderProgram(); renderHand(); };
```

要支援平板，這種地方必須改成「送出一個意圖，由主機決定」。我實際清點過全檔的事件處理器，分成四類：

### A. 設定畫面（開場前）— 不用動

`seg` / `segNum` / `renderNames` / `renderToggles` / `renderModes` / 目標分數滑桿 / 開始遊戲 / 規則按鈕。這些只在主機上跑。

### B. 會改變遊戲狀態的玩家動作 — 要改成意圖（約 10 個）

| 位置 | 動作 | 意圖名稱（建議） |
|---|---|---|
| `renderHand` 內 | 把手牌放進程式區 | `addCard` |
| `renderProgram` 內 `mc.onclick` | 收回程式區的卡 | `removeCard` |
| `renderProgram` 內 `minus`/`plus` | 迴圈夾住張數 ＋／− | `bumpSpan` |
| `renderHand` 棄牌勾選 | 標記／取消棄牌 | `toggleDiscard` |
| `#btnRun` | 執行 | `run` |
| `#btnClear` | 清空程式區 | `clearProgram` |
| `#btnEnd` | 結束回合 | `endTurn` |
| `#btnSwap` | 2 換 1 | `swap2for1` |
| `#btnDiscardMode` | 進入／離開棄牌模式 | `discardMode` |
| `#btnQuit` | 結束遊戲 | `quit`（只有老師能發） |

這部分單純，照著改就好。

### C. 執行中的互動選取 — **最棘手，要特別小心**（約 8 組）

這些是 `await pickXxx()` 形式，主機在執行引擎中途**暫停等待玩家點選**：

| 函式 | 用在哪 |
|---|---|
| `pickCell` | 專車接送、路障（點地圖格） |
| `pickPlayer` | 交換卡 |
| `pickSteal` | 病毒（偷資源） |
| 分配資源 `[data-mi]` / `[data-auto]` | 每回合結束把資源放上任務卡 |
| 2 換 1 的 `[data-i]` / `[data-get]` | 整理階段 |
| `chooseDirection` / 單人開場 `[data-dir]` | 開場選面向 |

在連線模式要變成：**主機送出「需要你選」的請求 → 平板顯示選取介面 → 平板回傳 → promise resolve**。這等於把一個本機的 promise 拉長成跨網路的往返。

**這是整個改造最容易出錯的地方**，要處理：

- 玩家在選的時候斷線怎麼辦（要有逾時 + 主機代為預設選擇）
- 回合限時倒數撞上選取視窗的互動（目前 `pauseTimer` / `resumeTimer` 的邏輯要重看）
- 主機端 `runNodes` 正在 `await`，不能讓它卡死

建議：**先把 B 類改完、跑過熱椅回歸測試**，確認意圖管線是對的，再動 C 類。
C 類在熱椅模式下可以維持原本的本機 promise（同一台機器，控制檢視直接顯示選取介面即可），
只有連線模式需要走跨網路版本——兩條路徑共用同一個 `pickXxx()` 介面。

### D. 純本機的畫面操作 — 不用動

看別人的任務卡（`viewPlayer`）、面板收合（`.pmin` / `.coltab` / `#btnFocus`）、規則說明、結算畫面按鈕、確認視窗。這些是各自裝置的視角，本來就該獨立。

## 6. 部署：不會影響線上版，有機制保證

查證過 Pages 設定：

```json
{ "source": { "branch": "main", "path": "/" } }
```

**Pages 只看 `main` 分支。** 所以：

1. 開一個分支（例如 `live-mode`）做這件事
2. `main` 完全不動 → <https://jack1214w.github.io/robot-city/> **一行都不會變**
3. 這段期間照樣可以用現在的版本上課
4. 等新模式在分支上測到滿意，才合併進 `main`

這不是「會小心」，是分支機制上就做不到互相影響。

### 檔案大小

`index.html` 目前 125,751 bytes。加上連線和平板版面大概會到 170KB 上下，單一檔案還撐得住。

真的大到難維護時再拆成 `index.html` + `game.js`，離線雙擊一樣能用（相對路徑，但要用傳統 `<script src>` 而不是 ES module——`file://` 會被 CORS 擋掉 module），只是不能再單檔寄給別人。**那不是現在要處理的事。**

## 7. 不可妥協的約束

1. **熱椅模式必須維持現狀可用。** 每個 Phase 做完都要把熱椅模式完整跑一輪回歸測試
2. **`main` 分支在合併前不得變動**
3. **規則邏輯只能有一份。** 不接受「投影版」和「平板版」各自維護一套卡片定義或執行引擎
4. **不引入雲端服務、不要求申請帳號、學生資料不出教室**
5. **離線可用的單檔特性**在熱椅模式下必須保留

---

## 8. 老師上課時要做的事（第一次交付後）

1. 雙擊桌面上的啟動檔
2. 投影畫面出現 QR code
3. 學生用平板掃碼、挑座位
4. 開始

macOS 第一次執行可能跳防火牆詢問視窗，按「允許」。（目前筆電防火牆是關閉狀態，很可能不會問。）

## 9. 給新對話的開場指引

開場可以直接說：

> 讀 `docs/平板連線模式-規劃.md`，在 `live-mode` 分支上做第一次交付。

一次做到「平板連線可用」，中間不要停下來等確認——第 4 節裡的內部檢查點
（熱椅回歸測試）是實作者自己跑的，不需要使用者參與。

第 2 節「還沒確認的」兩項（平板數量、其他教室）不影響動工，可以邊做邊問。
